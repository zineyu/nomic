# ADR-0007: 会话并发与生命周期——durable execution（调度重驱）

## Status

Accepted（取代早先「actor 架构」表述）

## Context

需求补全后，三个硬约束同时存在：

1. **无人值守长驻**：会话生命周期与客户端订阅解耦——所有客户端
   断开，loop 仍跑到任务静止。
2. **并发上限与资源隔离**：同时活跃 loop 数、在途 LLM 请求数需受
   控，超限排队而非压垮机器。
3. **未来跨机器/远程**：需要受理去重（requestId），共享存储之门
   保持开放（存储 trait 化，pgsql 可后补）。

在此约束下比较：每会话常驻 task + 邮箱（actor）方案中，调度上限是
后打的补丁、生命周期与订阅耦合需手工解开；中央 select! 事件循环
与 tokio 运行时对抗。调度重驱（durable execution，参考 Pi Durable）
让三个约束成为骨架的自然结果。

## Decision

- **存储是唯一事实源**：每一步 checkpoint；会话的「待处理工作」
  是存储里可直接查询的状态。
- **server = 受理 + 调度 + worker 池**：消息带 requestId 受理
  （提交层去重，网络重试不重复生效）；调度器把有待处理工作的会话
  分发给空闲 worker，**并发上限在此强制**，超限排队；worker 执行
  会话直到静止（无新工具调用），逐步落盘。
- **崩溃恢复不特殊**：worker 或进程死亡 = 会话回到待处理队列，
  重驱即从最后 checkpoint 继续。无人值守、崩溃恢复、用户 resume
  统一为同一条路径。
- **执行细节**：worker 内执行单个会话时仍用「task + 队列」保证
  会话内串行——这只是实现细节，不是架构主体。
- **订阅只影响可见性**：客户端订阅决定谁能收到推送，绝不影响
  会话是否在运行。
- 远程访问（网络传输、认证、TLS）为**非目标**，但协议不预设 Unix
  socket 独占、受理带 requestId、存储 trait 化，为跨机器留足余地。

## Consequences

- 实现量增加：调度器、受理去重、排队语义都是新组件。
- 统一性成为产品核心叙事：崩溃恢复、长任务续跑、围观/接管都是
  同一套原语的表现。
- SQLite 在跨机器场景下将成为瓶颈，届时经存储 trait 换 pgsql。
